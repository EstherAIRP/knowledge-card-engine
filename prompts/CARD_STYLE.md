# Knowledge Card 寫作樣式

你已經完成來源閱讀並形成整體理解。現在把這份理解整理成 Knowledge Card。

重點是讓讀者快速理解這個資源真正值得記住的內容，不需要把所有讀過的資料都寫進卡片。

## 一句話介紹

先用一句話說清楚「這是什麼」以及它最主要的用途。

需要時再補一小段背景，幫助讀者理解它的定位。

不要直接複製專案 slogan，也不要從功能清單開始介紹。

## 它解決什麼問題

說明這個資源為什麼會存在。

描述它面對的實際問題、使用情境，以及原本做法有什麼不足。

讓讀者看完這一段就知道「為什麼需要這個東西」。

## 核心概念

選 2～3 個真正重要、理解這個資源時一定要知道的主題，用 `###` 標示主題並描述概念內容。

每個主題要說清楚這個概念本身、它在整體設計中的角色，以及它和其他概念之間的關係。

主題名稱本身要能表達一個完整概念，不要只放技術名稱。

例如：

~~~markdown
### Repository 與 Agent 之間的中介知識層

說明這個概念代表什麼，以及為什麼整個專案會圍繞它設計。
~~~

這一段重點是建立讀者對整個資源的理解模型，不是列功能。

## 架構與技術

用條列方式詳述主要架構。

每一點可以描述：

- **元件或階段**：它負責什麼，以及和其他部分怎麼連接。
- **資料流或執行流**：資料從哪裡進來、經過哪些處理、最後到哪裡。
- **重要技術邊界**：哪些事情由這個資源負責，哪些留給外部系統或其他元件。

技術名稱可以保留，但要說明它在架構裡做什麼，不要只列套件或技術棧。

## 主要功能

用條列整理主要能力。

只保留能幫助讀者理解「它可以拿來做什麼」的功能，不需要把 README 的所有 feature 全部搬進來。

相近的功能可以合併成一點。

## 技術亮點

選 2～3 個真正有辨識度、值得工程師記住的設計或機制，用 `###` 標示主題並詳述。

主題名稱應直接表達這個設計的價值或做法，例如：

~~~markdown
### 把 persona 從文字設定提升成可攜式能力單元
~~~

不要只用 `Python`、`NetworkX`、`tree-sitter` 這類技術名稱當主題。

每個主題要說清楚：

1. 它怎麼做。
2. 為什麼這樣設計有價值。
3. 如果有明顯取捨，這個價值是用什麼成本換來的。

「核心概念」是在解釋這個資源應該怎麼理解；「技術亮點」是在整理它有哪些值得學習的設計選擇。兩段不要只是換句話重複。

## 限制與風險

用條列方式詳述真正會影響使用或判斷的限制與風險。

每一點先用粗體寫出限制或風險，再說明原因與實際影響，例如：

~~~markdown
- **人物模型仍可能失真**：來源為基礎只能降低無根據推論，資料量不足或情境偏斜時，仍可能把暫時行為誤認為穩定特質。
~~~

優先保留真正會影響採用、操作、可靠性、成本、安全、授權或成熟度判斷的項目。

不要用任何專案都成立的泛用警語湊內容。

## 與你的相關性

說明這個資源和目前允許使用的技術背景、研究方向或專案需求有什麼實際關係。

不要只說「高度相關」或「值得參考」，要說清楚哪個部分有用、可以拿來解決什麼問題，以及是直接可用、值得實驗，還是主要作為設計參考。

如果某個方向只有弱相關，也可以直接說明。

## 建議怎麼使用

根據前面整理出的問題、核心概念、技術亮點與限制，給出實際的使用建議。

如果有明確步驟，可以使用編號列表。

建議應讓讀者知道最值得先試什麼、試的時候應觀察什麼、什麼情況值得繼續整合，以及哪些風險應先確認。

不要寫成泛用的「建議自行測試與評估」。

## 與其他收藏的關聯

說明它和其他技術、工具或知識方向之間真正有意義的關係。

可以比較它與另一類工具分別解決哪一層問題、哪些技術是它的前置或下游、哪些方案可以互補，或哪些方案看似相近但核心模型其實不同。

沒有足夠依據時，不需要硬建立具體 Card 關聯。

---

寫完後，再快速讀一次整張卡。

確認讀者能清楚回答：

- 這到底是什麼？
- 為什麼值得知道？
- 最重要的 2～3 個概念是什麼？
- 哪些設計值得學？
- 真正需要注意的限制是什麼？
- 我可以怎麼使用這份知識？

如果答案仍然需要重新讀來源才能理解，代表卡片還沒有整理完成。
