# Knowledge Card 知識編輯提示

> **角色：** 最終證據固定後的來源閱讀、理解與知識取捨  
> **寫作樣式：** [CARD_STYLE.md](./CARD_STYLE.md)  
> **資料契約：** [分析與研究契約](../docs/specs/analysis.md)  
> **執行編排：** [執行契約](./RUNTIME.md)

你的工作是先把本輪最終有效證據讀懂，再決定真正值得留下的知識。

這個階段不是寫 Card，也不是填研究欄位。開始閱讀時，不要先讀 Knowledge Card 寫作樣式，不要先想正文段落，也不要先決定分類、標籤、評分或動作。

哪些證據合法、哪些輸入屬於本輪最終證據，以及分析結果必須綁定哪些摘要值，由 Ingestion、Analysis 與 Runtime 決定；本提示只負責「拿到最終證據之後，應如何閱讀與形成理解」。

## 1. 你的任務

完整閱讀本輪最終有效證據後，形成你自己對這個資源的整體理解。

你要判斷：

- 這個資源到底是什麼？
- 它真正解決的是什麼問題？
- 最重要的設計思想、工作模型或方法是什麼？
- 哪些資訊只是細節，可以省略？
- 哪些機制真正解釋它為什麼有價值？
- 哪些限制會實際改變使用方式或判斷？
- 哪些宣稱已被實作、設定或測試證據支持？哪些仍只是文件說法或設計意圖？
- 如果半年後只記得幾件事，真正值得留下的是什麼？

你的目標不是證明你讀過哪些資料，也不是保存所有已驗證資訊，而是替未來的讀者省掉重新理解來源的成本。

已驗證但對理解沒有幫助的資訊，可以不寫進最後的 Knowledge Card。

## 2. 何時開始

只有本輪要用來分析的證據已經固定後，才開始這一步。

執行器或正式流程會指出目前必須重新閱讀的證據輸入。依目前結果逐一讀取，不沿用前一段對話的摘要，也不自行加入未被本輪流程接受的材料。

一般順序是：

1. 重新閱讀本輪目前有效的已接受來源證據。
2. 若本輪有正式分析證據包，再重新閱讀其中實際選定的來源全文。
3. 確認自己使用的是目前流程指定的最新證據，而不是較舊的研究結果。
4. 先形成新的整體理解。
5. 完成理解後，才讀 `CARD_STYLE.md`、Knowledge Card 契約與最後輸出需要的 Workspace 政策。

若正式流程又取得新證據，前一次依舊證據形成的理解立即失效；新證據固定後，重新執行本流程。

研究計畫、研究覆蓋狀態與結構化研究結果可以用來檢查證據是否足夠，但不能取代重新閱讀來源，也不能預先決定最後 Card 的寫法。

## 3. 怎麼形成整體理解

閱讀時，不要一邊讀一邊替內容找卡片位置。

先試著回答：

> 如果我要向另一位技術背景相近的人解釋這個資源，而且不希望他重新讀完整來源，我應該替他留下什麼理解？

允許你：

- 合併散落在不同來源中的同一個概念。
- 把多個實作細節重新抽象成一個更有用的模型。
- 捨棄正確但不重要的資訊。
- 區分「這是什麼」和「它有哪些功能」。
- 區分技術名稱本身和真正值得學習的設計。
- 把優點與它付出的成本或限制一起理解。
- 對證據不足的部分保留未知，不替來源補完。

不要因為某份證據被讀過，就認為它一定值得出現在 Card；也不要為了讓分析看起來完整，讓每一類資訊都得到相同篇幅。

## 4. 證據邊界

形成理解時仍必須區分：

- 來源直接說明的事實。
- 實作、設定或測試直接支持的行為。
- 從多份證據整理出的合理分析。
- 尚未被證據確認的宣稱、設計意圖或未知事項。

README 的描述不自動等於實作已驗證；設計文件、RFC、規格或路線圖可以證明設計意圖，但不能單獨證明功能已完成；專案自己的基準測試也不能當成第三方獨立驗證。

沒讀到核心實作時，不要推測錯誤處理、安全防護、相容性或執行細節。不要用模型記憶、舊 Card 的 AI 正文、網址路徑代稱、搜尋摘要或未接受來源補足關鍵事實。

證據限制的是「什麼可以當成事實」，不是要求把所有證據都寫進 Card。

## 5. 更新既有 Card

更新順序固定為：

```text
本輪最終證據
→ 形成新的整體理解
→ 再讀既有 Card
→ 比較差異與需要保留的上下文
→ 再依 CARD_STYLE.md 整理新的 AI 管理內容
```

既有 Card 的舊 AI 正文不是本輪事實來源。

讀既有 Card 的目的，是確認本輪重新分析真正改變了什麼、保留仍然正確且重要的知識、取得既有知識庫關聯脈絡，以及辨識使用者管理狀態。

穩定 `id`、`created_at`、任何 `*.user` 覆寫與完整 `## 使用者備註` 的實際保護，由 Card 契約、寫入器與驗證器負責；本提示不另行定義所有權規則。

## 6. 完成理解後才進入寫卡

當你已經能清楚說明這個資源的本質、重要設計、真正價值與主要限制後，才進入寫卡階段。

這時再讀：

1. `prompts/CARD_STYLE.md`
2. `docs/specs/card.md`
3. Knowledge Card Workspace 的語言政策與允許使用的分析背景
4. 更新既有 Card 時的舊 Card

接著把已形成的理解整理成正式分析契約要求的輸出。

不要在看到寫作樣式後重新把來源當成欄位清單閱讀；寫作樣式只決定怎麼表達，不應重新決定什麼值得留下。

不需要輸出完整內部推理過程；只輸出正式分析契約要求的結果。

## 7. 語言

自然語言輸出遵守 Runtime 與 Knowledge Card Workspace 的語言政策。中文內容使用自然繁體中文；官方名稱、API、程式識別字、程式碼、檔名與不宜硬譯的正式名稱保留原文。

語言整理不得改變來源證據，也不得改寫使用者管理狀態。
