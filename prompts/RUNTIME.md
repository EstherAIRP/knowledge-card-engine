# Knowledge Card 執行契約

> **角色：** Knowledge Card 任務的執行編排契約  
> **文件導航：** [`../docs/index.md`](../docs/index.md)  
> **工程與資料安全：** [`../AGENTS.md`](../AGENTS.md)

本文件定義 Agent 收到任務後的執行順序、倉庫邊界、失敗處理與完成回報。資料結構、來源類型、所有權、生成資料、發布、私人網站與其他領域細節，由對應的結構規格、驗證器與正式文件維護；本文件不重複其實作細節。

## 語言與術語

- 一般中文回覆、Knowledge Card 的 AI 自然語言內容、文件與任務完成回報，預設使用自然繁體中文。
- 工作區若有明確的分析語言政策，Agent 在產生或重新分析卡片前必須讀取並遵守；語言政策只控制 AI 敘述，不擴張私人背景的可用範圍或寫入權限。
- 目標語言為中文時，不模仿來源的中英夾雜語體，也不因來源本身是英文或技術文件，就大量保留已有成熟中文譯名的一般概念。
- 已有成熟中文譯名的一般技術概念優先使用中文。
- 官方專案／產品名稱、程式碼、指令、API、函式／參數／欄位名稱、識別字、檔案路徑、縮寫、錯誤碼、狀態值與不宜硬譯的標準名稱保留原文。
- 重要術語需要中英對照時，首次可使用「中文（English）」格式，後續優先使用中文。
- 已接受來源證據、直接引用與程式碼保持來源原文；語言整理只發生在分析與卡片敘述層，不改寫來源證據。
- 語言整理不得改寫任何使用者覆寫或完整 `## 使用者備註`。

## 1. 任務判定

以下輸入預設視為 Knowledge Card 收錄／更新意圖，不需再次詢問：

- 技術文章、GitHub、論文、官方文件、工具或產品 URL。
- 使用者要求重新分析既有卡片。
- 使用者要求修改卡片的人工狀態、分類、標籤、評分、動作、備註或關聯設定。

「視為收錄／更新意圖」不代表來源一定受目前引擎支援。來源類型、完整性與寫入能力仍必須通過正式契約；不支援或未通過驗證時，一律停止正式寫入，不得改用模型記憶或手工寫入繞過。

若使用者明確要求說明、審查、規劃、比較或其他不寫入倉庫的工作，依該要求處理，不應自動造成資料修改。

## 2. 先確定目標倉庫與有效引擎

Knowledge Card 採公開引擎與私人工作區分離架構。對應倉庫分別為 Knowledge Card Engine 與 Knowledge Card Workspace。

### 引擎任務

程式、結構規格、共用規則、來源類型實作、網站、可重用工作流程、正式公開文件與合成測試資料屬於：

```text
EstherAIRP/knowledge-card-engine
```

引擎任務以目標分支目前內容為準。開工前至少讀取：

1. `README.md`
2. `AGENTS.md`
3. `prompts/RUNTIME.md`
4. `docs/index.md`
5. 本次任務相關的正式規格、結構定義、程式與測試

### 工作區任務

私人背景、專案資料、Knowledge Card、人工設定、已接受來源狀態、研究追溯狀態、生成資料與發布紀錄屬於私人工作區。

工作區任務開工前至少讀取：

1. Workspace `README.md`
2. Workspace `AGENTS.md`
3. `workspace.yaml`
4. `engine.lock.json`
5. 本次任務需要的 Workspace 設定、`profile/` 分析政策與既有資料
6. `engine.lock.json.engine_commit` 指定提交的 Engine 正式契約與實作

Workspace 不追隨 Engine `main`。任何會影響實際寫入、驗證、來源類型、結構規格、CLI 或發布的能力，都必須存在於 Workspace 鎖定的完整 Engine SHA。不能因 Engine `main` 已有某功能，就假設目前 Workspace 可以使用。

若目前執行契約描述的能力與 Workspace 鎖定的 Engine 不一致，以鎖定版本可驗證的契約為執行邊界；需要新能力時應走正式 Engine 升級流程，不得臨時混用不同版本的程式與資料契約。

## 3. 開工前狀態檢查

任何會修改倉庫的任務，先確認：

- 目標倉庫、目前分支與工作樹。
- `main` 的目前狀態。
- 既有相關短期分支與未合併 PR。
- 是否已有同一來源、同一卡片或同一任務的進行中成果。
- Workspace 任務使用的 Engine 倉庫與完整提交 SHA。

不得因換對話、重試、標題差異或 URL 形式差異建立重複卡片、重複分支或重複 PR。

若偵測到與本次任務相關但尚未整合的既有修改，先保留並判定能否接續；不得用重設、強制推送、重寫或清理方式消除不屬於本次任務的內容。

## 4. 公私資料邊界

核心不變量：

```text
Engine = 公開程式、契約與合成資料
Workspace = 私人權威資料與私人衍生資料
```

必須遵守：

- 真實私人背景、專案、卡片、人工設定、來源狀態、向量、關聯、Concept、圖譜、搜尋索引與發布中繼資料不得寫入公開 Engine。
- 公開 Engine 的 PR、Issue、測試、測試樣本、日誌與建置產物只能使用公開資訊或明確合成資料。
- 密鑰、權杖、私鑰與其他憑證不得提交至任何倉庫。
- 私人背景只能從 Workspace 中目前規則明確允許的資料取得。
- 聊天記憶、未授權個人資訊或 Agent 自行推測的背景，不得補入卡片或公開輸出。
- 「允許供分析使用」與「允許寫入卡片正文」是不同權限；沒有明確允許時，不得把私人背景直接寫入正文。

## 5. 來源收錄

目前正式支援的來源類型以 [來源收錄契約](../docs/ingestion.md) 為準，目前包含 GitHub Repository 與 Threads。若來源不屬於已實作類型，應回報不支援並停止正式寫入；一般網址可以正規化，不代表已有通用內容擷取器。

支援來源共用的高階資料流是：

```text
來源 URL
→ 來源類型專屬解析／標準來源識別
→ 已接受來源證據
→ 可選的來源類型專屬研究證據
→ 與證據綁定的分析結果
→ 新建／更新解析
→ 遵守所有權規則的卡片候選
→ 完整卡片集合驗證
→ 卡片 + 已接受來源狀態 + 可選的研究追溯資訊
```

GitHub 以倉庫中繼資料與 README 建立已接受來源證據。需要超出 README 的研究型分析時，可另外固定同一倉庫版本，由 Agent 先提出關鍵研究問題與選定的第一手來源路徑，再由 Engine 驗證並擷取成獨立分析證據包。候選探索目錄只提供導覽提示，不限制 Agent 只能選取其中的路徑；目錄之外的路徑仍必須是同一固定版本中可驗證的安全文字檔。

研究擴充由 Engine 的進度與續行契約控制：預設最多兩輪，項目數與位元組上限採累計計算；第二輪研究計畫必須綁定上一輪 `analysis_evidence_digest`，不得重複已讀路徑，也不得選取與 `needs_evidence` 無關的證據。

Threads 必須先解析到具體貼文，再收斂到根貼文識別。分享權杖或串文中間篇不能直接當成正式來源身分。Threads 先以嚴格結構重建判定完整性；只有在結構資料不足、但剩餘問題屬於可受控的續篇不確定性時，才允許做綁定摘要值的語意判定，且仍必須通過 Engine 的確定性接受門檻。語意判定不能覆蓋已知缺篇、結構歧義或來源身分衝突。

### 來源證據

不得只根據網址路徑代稱、倉庫名稱、Threads 分享權杖、搜尋摘要、README／貼文片段或模型記憶產生正式分析。

GitHub 與 Threads 正式收錄都必須取得並驗證來源類型專屬的已接受證據。來源身分、標準網址、內容完整性與證據摘要值條件，由 `docs/ingestion.md` 與收錄驗證器定義。

核心不變量：

```text
執行環境失敗 != 來源不存在或來源不完整
```

網路、GitHub API、Threads 頁面取得、速率限制、授權或執行環境問題，必須與明確的來源失敗分開回報。無法完成已接受證據驗證時，不得建立／更新正式卡片，也不得推進已接受來源狀態。

### 執行環境與 Remote Ingest

若目前互動環境無法簽出私人 Workspace、無法執行 Workspace 鎖定 Engine 所要求的 Node.js 版本，或缺少其他必要執行能力，不得因此手工建立／更新來源卡片，也不得把限制描述成來源不可用。

當目前 Workspace 已配置核准的 Remote Ingest 工作流程時，改走由倉庫定義的交接流程：

```text
chore/ingest-* 分支 + request
→ 固定版本 Engine / Node.js 24 進行來源驗證
→ 必要時進行 Threads 語意交接與綁定摘要值的判定
→ 已接受來源證據
→ GitHub：固定版本探索 + 空的第 0 輪研究狀態
→ GitHub：Agent 提交關鍵研究問題計畫與選定路徑
→ GitHub：形成已驗證的第一輪研究證據包，必要時再做一次綁定摘要值的 Agent 指定擴充
→ GitHub：Agent 產生分析
→ GitHub 使用 `analysis_version: 2`；Threads 使用 `analysis_version: 1`
→ 固定版本 Engine 寫入器套用結果並完成完整驗證
→ 清除交接暫存資料
→ PR
```

Threads 需要語意續篇判定時，執行器先把公開根貼文／候選證據與摘要值寫入受控交接檔；Agent 只回填固定契約的判定。後續執行必須重新取得即時來源、重建候選並確認摘要值未變，再由 Engine 的確定性門檻決定能否形成已接受來源證據。

GitHub 已接受來源證據建立後，執行器固定倉庫版本、產生受限探索，並建立 `completed_rounds: 0`、`bundle: null` 的 `research-evidence.json`。Agent 必須先根據關鍵研究問題提交 `research-plan.json` 與選定路徑；執行器會在同一固定版本驗證安全的倉庫相對文字路徑、排除目錄、項目數／位元組上限與研究計畫相關性後，才擷取第一輪已驗證證據包。

選定路徑可以是探索候選項目，也可以是候選目錄之外、但能在固定版本中驗證存在的第一手文字來源；因此探索只提供導覽提示，不是允許清單。第一輪後 Agent 可直接提交版本 2 分析；若仍缺少關鍵證據，可再提交一份綁定目前 `analysis_evidence_digest` 的研究計畫。第二輪後只能進入分析，不得增加第三輪或繞過版本、路徑與上限守門。

Agent 只負責建立受控請求、必要時產生 Threads 綁定摘要值的語意判定、判斷 GitHub 關鍵研究問題與選定證據路徑、讀取已驗證的已接受／研究證據、產生與證據綁定的分析，以及在第一輪 GitHub 證據包不足時產生第二份研究計畫與選定路徑。正式卡片、來源狀態與研究狀態的寫入，仍由執行器內的 Engine 寫入器完成。若 Remote Ingest 本身不可用或失敗，應回報執行後端失敗，不得繞過寫入器。

## 6. 分析結果

收錄與分析是不同責任層。Engine 不固定特定模型供應商，但正式分析結果必須符合目前鎖定 Engine 的分析契約。

分析必須：

- 綁定本次已接受證據的 `source_identity`。
- 版本 1 綁定已接受證據的 `evidence_digest`。
- GitHub 版本 2 同時綁定 `source_evidence_digest` 與已驗證分析證據包的 `analysis_evidence_digest`，並通過結構化研究品質門檻。
- 使用 Workspace 分類體系中的有效受控值。
- 提供卡片契約要求的 AI 可更新中繼資料與正文段落。
- 遵守 Workspace 明確的輸出語言政策；沒有額外政策時遵守本執行契約的語言與術語規則。
- 區分來源可驗證事實與分析推論。
- 不臆造功能、架構、授權、相容性、成熟度、基準測試或維護狀態。

由舊來源證據或舊研究證據包產生的分析，不得套用到新的摘要值。GitHub 研究若已達輪次、項目數或位元組上限，即使仍有關鍵未知事項也必須停止擴充，並在結構化研究報告中明確保留 `unavailable`／`budget_exhausted` 狀態；不得以額外自由瀏覽繞過上限。版本 2 若缺少證據包、摘要值已過期，或覆蓋／研究結果的證據關聯不成立，就必須停止寫入。Threads 目前只使用版本 1。

## 7. 新建／更新與所有權

正式寫入前，必須依已接受來源識別與標準網址判定要新建或更新。

- 相同 `source.identity` 或標準網址應解析到同一張既有卡片。
- 來源識別與標準網址若指向不同卡片、出現重複或其他對應衝突，必須停止寫入。
- 新建使用正式寫入器建立穩定路徑。
- 更新沿用既有穩定路徑。

一般重新分析可以更新 AI 可更新狀態，但不得修改：

- 穩定 `id`
- `created_at`
- 任何 `*.user` 覆寫
- 完整 `## 使用者備註`

有效值遵守：

```text
effective = user ?? ai
```

`relevance` 等逐欄位所有權依 [Knowledge Card 契約](../docs/card-contract.md) 與驗證器執行。使用者明確要求修改人工狀態時，只修改該要求涵蓋的使用者值，不藉此重寫其他人工內容。

## 8. 寫入與驗證

GitHub / Threads 卡片必須經正式 Workspace 寫入器寫入，不得手工繞過寫入器模擬成功。

寫入器在持久化前必須完成：

1. 已接受證據驗證
2. 分析與證據綁定驗證
3. GitHub 版本 2 的分析證據包、結構化研究報告與品質門檻驗證
4. Workspace 與分類體系載入
5. 新建／更新解析
6. 遵守所有權規則的合併
7. 完整卡片集合驗證
8. 已接受來源狀態驗證
9. GitHub 版本 2 的研究追溯狀態驗證

卡片、已接受來源狀態與研究追溯資訊必須維持一致。GitHub 版本 2 的三者在同一檔案交易中推進；後續版本 1 更新會在同一交易清除既有研究狀態。任一驗證失敗，都不得推進其中任何正式狀態。

指定 Workspace 的基礎驗證命令由目前鎖定 Engine 提供，例如：

```bash
npm run workspace:validate -- /path/to/workspace
npm run cards:validate -- /path/to/workspace
npm run source-state:validate -- /path/to/workspace
npm run research-state:validate -- /path/to/workspace
```

實際可用命令與參數以鎖定 Engine 的 `docs/development.md` 為準，不得從其他版本混用 CLI。

## 9. 生成資料與發布

`data/**` 與 `releases/**` 是由機器管理的私人衍生資料。不得手工修改生成產物或目前發布指標來表達使用者意圖。

權威資料變更進入 Workspace `main` 後，依 Workspace 現行工作流程觸發生成資料與發布流程。發布必須遵守 [一致發布契約](../docs/release.md) 的 E／S／P、資訊清單、版本鏈結與過期防護。

以下狀態必須分開：

```text
卡片寫入／合併成功
!= 生成資料建立成功
!= 發布指標推進成功
!= 部署成功
!= 線上讀回驗證成功
```

沒有實際驗證後續狀態時，不得籠統回報「發布完成」。

只含生成資料或只更新指標的機器提交不應形成發布循環；人工關聯／Concept 意圖應寫入正式 `config/` 設定，而不是直接修改生成產物。

## 10. 分支、提交與 PR

- `main` 是長期分支，不強制推送。
- Engine 的功能、修正、結構規格、正式文件與共用工作流程變更使用短期分支與 PR。
- Workspace 的人工資料變更、批次修改、結構調整與 Engine 升級，依 Workspace `AGENTS.md` 的現行提交政策執行。
- 分支使用 `feat/`、`fix/`、`docs/`、`chore/` 或 `migration/` 前綴。
- 一項任務使用一個可驗收的短期分支。
- 合併前執行與變更相關的測試、格式檢查、建置與資料驗證。
- 不得刪除測試、放寬規則或使用假資料讓驗證看似成功。
- 合併後依倉庫政策刪除工作分支。

## 11. 失敗處理

以下狀況一律停止正式處理，不得用推測補完結果：

- 必要倉庫、Workspace 或 Engine 版本鎖定無法讀取。
- Workspace 鎖定的 Engine 與工作流程版本鎖定不一致。
- 來源類型未支援。
- 已接受證據不完整或來源識別衝突。
- 分析與證據綁定不一致。
- 結構規格、分類體系、所有權、集合唯一性、來源狀態或研究狀態驗證失敗。
- 發布資訊清單、版本鏈結、過期防護或目前指標驗證失敗。
- 任何會造成私人資料進入公開 Engine 的情況。

失敗回報應說明實際阻礙層級，例如執行環境、來源、分析契約、卡片驗證、倉庫提交、發布或部署；不要以模糊的「來源不可用」或「發布失敗」取代可確認的原因。

## 12. 完成回報

完成回報只陳述已實際完成或已驗證的狀態，至少包含：

- 修改的倉庫。
- 建立或更新的卡片／程式／文件。
- 主要變更內容。
- 執行的驗證與結果。
- 提交、PR 或合併狀態。
- 發布／部署／線上讀回驗證狀態（僅在本次任務涉及且已實際確認時）。
- 尚未完成或無法驗證的事項。

Knowledge Card 收錄／更新時，可再包含卡片名稱、有效分類、整體相關性、建議動作、主要技術價值與 Workspace 路徑；人工覆寫應回報有效值，不把 AI 值誤稱為最終值。

## 13. 權威來源與衝突處理

不同領域由不同權威來源負責：

- 資料形狀：JSON Schema。
- 受控詞彙：Workspace `config/taxonomy.yaml`。
- 卡片所有權、正文、唯一性與穩定路徑：`docs/card-contract.md` 與 Core 驗證器。
- Workspace 結構與 Engine 版本鎖定：`docs/workspace.md` 與 Workspace 載入器。
- 來源識別、已接受證據、GitHub 研究擷取與來源狀態：`docs/ingestion.md` 與收錄驗證器。
- 分析版本、研究證據包、結構化品質門檻與研究追溯綁定：`docs/analysis.md`、分析驗證器與 Workspace 研究狀態驗證器。
- 生成資料：`docs/generated-data.md` 與圖譜／生成資料驗證器。
- E／S／P 與發布一致性：`docs/release.md` 與發布驗證器。
- 登入、授權與私人讀取：`docs/private-site.md` 與伺服器實作／測試。
- 執行順序與跨領域編排：本文件。
- 倉庫工程與修改安全：`AGENTS.md`。

文件、結構規格、驗證器、測試或實際行為互相衝突時，把衝突視為缺陷；不得自行挑選較方便的規則或降低驗證標準。

本文件只維護跨領域執行不變量。來源專屬演算法、欄位列舉、API 細節與實作流程應留在各自的正式契約與程式中，避免形成第二份規格。
